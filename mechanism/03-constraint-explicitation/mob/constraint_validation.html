约束显化 Constraint Externalization

把隐含的语义假设变成显式规则——说一次，永久生效

设计师脑子里的"这个要危险一点"——评审会上说了三年，AI 一个字都没读到。约束显化把它从空气里搬出来，写成机器可读的 YAML 契约，再编译为 Prompt 前缀、JSON Schema、Checklist、CI 规则。

说一次，永久生效。

问题

一个循环往复的困境

"同一个'危险'，我在评审会上说了三年"

"同一个'危险'，我在评审会上说了三年。每换一个工程师、每开一条新产品线，就要重新说一遍。"

设计师在评审会上说："这个删除按钮太危险了，不能做得和普通按钮一样。"工程师点头，改了。三个月后，另一个团队用同样的 AI 工具生成后台管理界面，删除用户按钮又是蓝色实心。

问题不是"工程师没记住"，也不是"设计师没说清"——而是"危险"这个判断从未离开过设计师的脑子。它存在于评审会的空气里、Figma 注释里、某篇 Wiki 的角落里，但从来没有存在于机器能读到的地方。

断链

AI 没有上下文补偿能力

为什么隐性知识守不住

传统时代 · 隐性知识勉强够用

设计师和工程师坐在一起，口头传递语义判断："这个要做得危险一点。"工程师凭经验理解"危险"意味着红色、加确认框。

本质：人在替格式缺口打补丁。补丁打得了一时，打不了规模。

AI 生成时代 · 隐性知识彻底断链

AI 只消费显式输入：Prompt 里的文字、组件库的参数。设计师说"这个按钮要危险一点"，AI 听不到——这句话不在任何它消费的输入里。

结果：AI 按概率生成最"常见"的按钮——蓝色实心主按钮。

关键判断

语义漂移不是 AI"做错了"，而是约束从未被显式传递，AI 根本没有收到信号。归因为"AI 理解力不够"是等待更强的模型；归因为"约束不在输入里"才会去修约束的形态。前者是等待，后者是工程。

核心

四项能力

不是"把规范写成代码格式"，而是转换出传统形态原理上不可能提供的能力

1

规则必须带"违约动作"

从"建议"变成"阻断"——每一条"不能做什么"都必须附带"违反了怎么办"。

immutable_boundaries:
 - boundary_type: "safety"
   rule: "禁止所有错误状态共用同一种红色视觉表达"
   violation_action: "block"  # 不是 suggest，是 block
 - boundary_type: "clarity"
   rule: "每个错误级别必须提供明确的用户行动指引"
   violation_action: "warn"   # 不是 note，是 warn

走查阶段

人眼看到红色，圈出来让前端改 → 来回三轮

阻断阶段

AI 生成时用了红色 → 机器直接拦截，错误不出现

2

规则只能有一个"真身"

从"五份规范"变成"一份源头"——YAML 是真身，Prompt / Checklist / CI 规则全是自动编译产物，禁止手写副本。

ERR-001.yaml（真身）

→ Prompt 前缀 给 AI

→ JSON Schema 给前端

→ Checklist 给设计师

→ CI 规则 给流水线

四种格式全部自动编译，零手写副本

改前

改一处规则手动追四处 → 漏一处就是版本分裂

改后

改 YAML 真身一处，四处编译产物自动同步 → 零遗漏

3

规则要放在生成之前

从"事后检查"变成"前置拦截"——同一条"限流提示用黄色"的规则，放在不同环节，成本天差地别：

上线后发现用户已投诉成本最高
走查时发现代码已写完成本高
提交时拦截代码未合并成本中
生成前注入错误不出现成本零
# 同一条规则，在四个时刻接力
# 1. 生成前：Prompt 前缀前置注入
llm_constraints:
 - "限流提示必须使用 status.warning（黄色）"
 - "禁止在 retryable 级别使用 status.critical（红色）"

# 2. 编码时：JSON Schema 校验
properties:
 color_token:
   enum: ["status.neutral","status.warning","status.info"]
   not: { const: "status.critical" }

# 3. 提交时：CI 规则拦截
rules:
 error-severity-color:
   forbidden: { color: "#cf1322" for: "retryable" }
   action: "block"

# 4. 走查时：Checklist 人工复查
- [ ] 限流提示是否为黄色？
- [ ] 是否未使用红色？
4

只显化有证据的

从"拍脑袋"变成"有凭据"——规则入典必须有门槛：不是"我觉得"，而是"我测到了"。v1.0.0 只收录 6 个有充分证据的模式：

编号域问题证据来源
ERR-001Error后果差异未分级通用 AI 对话产品（流式中断/限流/网络故障）· ChatGPT / 文心 / 通义
PRO-001Process认知阶段未显化AI 搜索/多步推理产品（过程标签模糊）· Perplexity
BND-001Boundary权利差异未区分通用 AI 对话产品（拒绝与终止视觉混淆）· Claude
ACT-001Destructive高危操作未约束AI 生成后台/设置界面（删除按钮样式统一化）
ALR-001Synonym文案语义降级AI 运维/客服系统（关键术语被同义词替换）
INF-001Info状态权重未对齐AI 协作/创作工具（通知与警告视觉权重相同）

✗ 拍脑袋规则："我觉得按钮应该大一点" → 无证据，不入典

✓ 有凭据规则："我测到 6 类通用 AI 产品的限流提示都用了红色，用户反馈看不懂" → 有证据，入典

视角

角色视角

约束显化后，五个角色的处境变化

🎨 设计师与产品经理

"同一个'危险'，我在评审会上说了三年。每换一个工程师、每开一条新产品线，就要重新说一遍。"

解法：action.destructive 注册入典，绑定红色空心 + 二次确认 + 不可恢复文案。判断显化一次，全组织永久引用——不再重复说"危险"，改说"查字典"。

验证：新团队、新产品线生成删除按钮时，约束自动在场，无需任何人口头传递。

💻 前端 / AI 工程师

"规范文档四百页，我不可能每次写代码前重读一遍。AI 更不可能。"

解法：契约编译为 Prompt 前缀前置注入 AI 上下文，约束从"需要被想起"变成"已经在场"。

验证：AI 输出对约束的命中率不再依赖任何人的记忆——约束编译成 Prompt 前缀、Schema 和 CI 规则，在你工作之前已经在场。

📋 DesignOps

"规范改了一处，三个月后抽查发现一半团队还在用旧版——没人是故意的，只是没人知道变了。"

解法：字典变更走 PR，触发全量重编译，四种消费格式同步换版，引用方收到影响面报告。

验证：第一次能回答"这次变更影响了哪些契约、哪些团队"——精确到清单，而非"应该都通知到了"。

🏗 语义翻译设计师

"我的经验在公司十年，评审时能一眼看出问题——但我讲不清我是怎么看出来的，更别说让机器看出来。"

解法：专家的判定逻辑被结构化为关键词表、类型规则、校验项——直觉翻译成规则后，可被复核、可被传授、可被机器执行。

验证：专家休假时，诊断照常运转；"一眼看出"变成组织的"逐层可验"。

📊 管理层

"团队最大的隐性成本是'重复传递同一句判断'。"

解法：约束显化是一次性投资：判断显化入典后，传播零成本、执行有机器保障、变更有账可查。

验证：约束从"口头资产"变成"组织资产"——有版本、有引用方、有折旧、有审计轨迹。
