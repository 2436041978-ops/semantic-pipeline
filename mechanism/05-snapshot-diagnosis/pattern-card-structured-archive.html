模式卡片 Pattern Card

诊断出来的语义漂移，写成散点案例和写成模式卡片，到底有什么实际差别？
不是"有没有记录"，而是"记录了什么结构，让机器和人都能复用"。

1

复用成本差异

散点案例：每次从零诊断 2 小时。模式卡片：引用确认 10 分钟。

6 字段解决 4 项不可见

不可检索、不可复用、不可演进、不可度量 → 结构化后全部解决。

同一次语义漂移，两种记录方式

ERR-001：错误状态后果差异未分级

Before · 散点案例

形态 A：截图文件夹

/走查记录/
ChatGPT_错误状态_红色混乱.png
文心一言_连接断开_红色.png
Kimi_429_红色.png
DeepSeek_服务异常_红色.png

❌ 文件名即全部信息，没有根因、没有修复路径

形态 B：Excel 表格

产品 │ 组件 │ 问题描述 │ 优先级
ChatGPT │ 错误状态 │ 四种错误共用红色 │ P1
文心一言 │ 错误状态 │ 连接断开用红色 │ P2
Kimi │ 错误状态 │ 429 用红色 │ P2

❌ "问题描述"只有现象，没有根因+后果，检索不出来

形态 C：语雀文档片段

"ChatGPT 的四种错误状态共用同一种红色，用户无法判断后果严重程度。文心一言和 Kimi 也有类似问题。建议错误状态分级显示。"

❌ 对人可读，对机器不可查；没有 pattern_id，没有与令牌表绑定

After · 模式卡片

pattern_id: "ERR-001"
component_type: "错误状态"
name: "后果差异未分级"
description: |
  症状：流式中断 / 网络故障 / 限流 / 服务异常
        四种错误同红
  根因：缺少 error_severity 语义令牌
        前端只接收 isError = true 布尔值
  后果：用户无法判断后果严重程度
        不知道该刷新还是等待
preview: "patterns/ERR-001/preview.png"
evidence:
  - "ChatGPT"
  - "文心一言"
  - "通义千问"
  - "Kimi"
  - "DeepSeek"
✓ pattern_id：精确指向，跨产品关联
✓ component_type：标准化枚举，机器可检索
✓ description：现象+根因+后果，机器可判定
✓ evidence：5 个产品，覆盖度可统计

复用成本量化对比

设计师 B 遇到文心一言的红色混乱，两种记录方式的实际成本

散点案例 · 2 小时

2h 00min — 重新诊断
1. 截图存档（5min）
2. 翻查历史记录，找不到同类问题（15min）
3. 重新分析根因：为什么是红色？（30min）
4. 写走查报告：现象+建议（40min）
5. 与前端沟通：该生成什么契约？（30min）
6. 等待前端理解并修复（20min）

❌ 每次从零开始，团队积累 100 个截图，无法统计

模式卡片 · 10 分钟

10min — 引用确认
1. 检索模式库：component_type = "错误状态"（2min）
2. 找到 ERR-001，查看 description 确认同一根因（3min）
3. 检查 evidence 列表：文心一言已收录（1min）
4. 引用 ERR-001 契约模板，直接生成约束（3min）
5. 提交 PR，CI 自动校验（1min）

✓ 一次诊断，全团队复用。N 个产品 × M 个模式覆盖矩阵一目了然

关键差异

散点案例的"详细化"是信息层面的——多写几个字、多截几张图。
模式卡片的"结构化"是资产层面的——增加 pattern_id 让记录可引用，增加 component_type 让记录可检索，增加 evidence 让覆盖度可统计。

这些结构让一次诊断变成组织级可复用资产。

诊断不是"写完了就完事"，是组织资产的增厚

模式卡片横跨 Guard → Contract → Verify 三阶段，诊断→修复→验证全链路可追溯
