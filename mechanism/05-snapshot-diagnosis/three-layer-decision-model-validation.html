⑥ 三层判定模型：为什么归因必须分三层，而不能一步到位

三层判定模型验证 Three-Layer Model

验证"一步到位"的主观归因为什么失效，三层判定如何使语义诊断可复现、可审计、可回溯。
以 ERR-001 错误状态后果差异未分级为示例，走完三层判定的完整链路。

1

一步到位的主观判断为什么失效

四个角色的真实反馈：调整前的诊断困境

A

体验架构师

"我判断这是 ERR-001（错误状态后果差异未分级），另一个架构师判断这是 ALR-001（告警文案语义降级）。

谁也说服不了谁——我们的推理过程都是黑箱。"

D

设计师

"走查会上我说'这是错误分级问题'，工程师反问'你怎么确定的'，我答不上来，只能说'经验'。

但经验无法被复核，也无法被新人继承。"

F

前端工程师

"产品说'语义有问题'，我问哪里有问题，对方说'整体感觉'。

我不知道该改颜色、改文案还是改交互——没有分层，就没有改动的优先级和范围。"

O

DesignOps

"上个月归档的问题清单，这个月抽查发现错了三条——但没人知道是看错、判错还是记错，只能全部重查。

一步到位的归档没有审计路径。"

一步到位失效的共同特征

四个角色面对同一个红色 Alert，给出了四个不同的模式判断。分歧的根源不是"谁的经验更准"，而是一步到位的归因把三个正交问题压缩成了一个黑箱结论：
• 分类问题（这是什么组件？）被跳过了
• 缺失问题（缺了什么语义？）被混在感受里了
• 表达问题（视觉映射对不对？）被当成了"整体感觉"

当三个问题被压缩成一个答案时，任何两个人给出不同答案都是正常的——因为他们在回答的是三个不同的问题，只是没有意识到。

三层 vs 一步到位：正交问题对照

正交问题 一步到位（黑箱） 三层判定（白箱）
这是什么组件？ 被跳过，直接跳到模式判断 Layer 1 明确回答，输出组件标签
缺了什么语义？ 混在"感觉"里，无法提取 Layer 2 提取语义关键词，匹配缺失模式

3

三层判定执行流程

逐层解耦，每层有输入、规则、输出、短路条件

Layer 1 组件类型识别

回答：这是什么组件？

消费字段

component_type + context

输出标签

Alert / Message（错误提示）

短路条件

无法归类 → 提示补 context

Layer 2 语义缺失判定

回答：缺了什么语义？

消费字段

user_confusion

输出标签

error_severity 语义令牌缺失

短路条件

无关键词命中 → 提示补 user_confusion

Layer 3 视觉表达校验

回答：视觉映射对不对？

消费字段

visual_record

输出标签

颜色映射不匹配（全部红色）

短路条件

无视觉偏差 → 标记为语义层问题

诊断完成

三层标签：Alert → error_severity 缺失 → 颜色映射不匹配 → 归属模式 ERR-001

调整前 · 一步到位

核心结论

语义诊断不能一步到位，因为三个正交问题被压缩成一个黑箱结论时，任何两个人给出不同答案都是正常的。

三层判定模型将归因拆解为三个可独立验证的步骤：
• Layer 1 回答"这是什么组件"——按交互路径分类，而非视觉形态
• Layer 2 回答"缺了什么语义"——提取用户困惑中的关键词，匹配缺失模式
• Layer 3 回答"视觉映射对不对"——逐项校验颜色、文案、行动偏差

每层有明确的消费字段、合法判据和短路条件。分歧可以定位到具体层级，误判可以回溯到具体步骤，证据不足时可以短路阻止低质量结论进入模式库。

三层判定不是增加了复杂度，而是把原本隐藏在"经验"中的推理过程显式化、可审计、可继承。
