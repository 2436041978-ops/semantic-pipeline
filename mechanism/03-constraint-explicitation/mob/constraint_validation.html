隐含假设暴露

当前 AI 工具的隐含假设是："所有错误状态都应该用红色表达"。这个假设从未被写成规则，但深深嵌在 Prompt 和组件库中。结果是：限流（retryable）和系统崩溃（fatal）长得一模一样，用户不知道是该刷新还是该等待。

Layer 1 · 组件类型

错误提示（Alert / Message）

Layer 2 · 语义缺失

后果差异未分级 · 恢复路径不明确

Layer 3 · 视觉校验

颜色映射不匹配 · 所有错误共用红色

STEP 2 · 已编译

生成显式规则

Contract Library · 把隐含假设写成机器可读的 YAML 契约

✕ 约束显化前（隐含）

# 没有规则文件
# 设计师心里知道："严重错误用红色"
# 前端心里知道："Alert 组件默认红色"
# LLM Prompt 里写："错误提示用红色背景"
# 结果：所有错误都是红色
# 用户无法区分 fatal / transient / retryable

✓ 约束显化后（显式）

intent_id: "ERR-001"
semantic_tokens:
  error_severity:
    fatal:     { color_token: "status.critical",
                 motion_token: "pulse.red.urgent",
                 icon_token: "alert.octagon" }
    transient: { color_token: "status.neutral",
                 motion_token: "spinner",
                 icon_token: "loader" }
    retryable: { color_token: "status.warning",
                 motion_token: "none",
                 icon_token: "clock" }
    degraded:  { color_token: "status.info",
                 motion_token: "none",
                 icon_token: "info.circle" }
immutable_boundaries:
  - boundary_type: "safety"
    rule: "禁止所有错误状态共用同一种红色视觉表达"
    violation_action: "block"

FATAL

status.critical · pulse.red.urgent

TRANSIENT

status.neutral · spinner

RETRYABLE

status.warning · clock

DEGRADED

status.info · info.circle

核心动作：把散落在设计师脑子、产品文档、前端组件默认值里的隐含语义假设，提取成一份机器可读的 YAML 契约——semantic_tokens 定义 4 个级别，immutable_boundaries 用 safety 边界禁止"所有错误都用红色"。

STEP 3 · 已验证

证明规则有效

Validation Toolkit · 语义分级器验证显化前后对比

✕ 显化前 · 隐含假设支配

🔴 请求过于频繁，请稍后再试

❌ 红色 Alert，用户不知道是刷新就好还是对话已丢
color: #cf1322（硬编码）· background: solid red（组件默认值）· action: 无指引

✓ 显化后 · 显式规则支配

⏱️ 请求频率已达上限 · 请在 42 分钟后重试，或升级 Plus

✓ 黄色提示 + 时钟图标 + 明确行动指引（等待/升级）
color_token: status.warning · icon_token: clock · action: wait_countdown / upgrade（均来自 YAML）

RETRYABLE

限流/流控，用户可自助恢复

# 语义分级器输出
input: "请求过于频繁，请稍后再试"
matched_severity: "retryable"
confidence: 0.95
applied_rules:              # ← 全部来自 ERR-001.yaml

  - icon_token: "clock"

  - immutable_boundary.clarity: 通过（提供明确行动）
