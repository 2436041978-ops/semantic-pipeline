E

案例一 · ERR-001 错误状态诊断

三层判定，把"全红"拆成四级

现象

四种错误，同一种红色

流式中断 / 网络故障 / 限流 / 服务异常

Fatal 致命错误

服务不可用，用户无法自助恢复

Transient 瞬时错误

网络抖动，可自动重试

Retryable 可重试错误

限流 429，等待后可恢复

Degraded 降级错误

功能部分可用，影响有限

❌ 四种后果完全不同的错误，共用同一个 red-500，用户无法判断严重程度

证据

跨产品证据 · 6 款 AI 产品

不是个案，是行业普遍现象 · 左右滑动

产品错误表现颜色后果可辨？
ChatGPT中断/网络错误同红 Bannerred✗
文心一言连接断开与限流同红red✗
通义千问错误统一红色 Toastred✗
Kimi429 限流红色提示red✗
豆包服务异常红色 Bannerred✗
DeepSeek繁忙与失败同红色red✗

用户抱怨（Reddit / V2EX / 即刻）

"红了一片，不知道是服务器挂了还是我网断了。"
"429 限流也红、崩溃也红，我到底该不该刷新？"
"看到红色第一反应就是'完了'，结果只是限流。"

根因

isError=true 的语义缺失

布尔值 → 四级枚举的语义升维

BEFORE · 后端只传一个布尔值

{ isError: true }  // 前端只能映射到一种红色
→ 四级错误后果全部坍缩为"红了"

AFTER · error_severity 四级枚举

{ isError: true,
  error_severity: "fatal | transient | retryable | degraded" }
→ 每级错误有独立的颜色/文案/行动映射
方法

三层判定模型

L1 类型识别 → L2 语义缺失 → L3 视觉校验

L1

组件类型识别

判定该界面属于"错误状态"组件（红色 Banner + 错误文案 + 阻塞交互），进入 ERR 类诊断通道

L2

语义缺失判定

检查是否存在 error_severity 分级语义。结果：缺失 —— 四种错误共用 isError=true 单通道

L3

视觉表达校验 · 4 特征

① 颜色映射不匹配 ✗ 四级共用 red-500

② 文案精度不足 ✗ "出错了"未区分后果

③ 行动完整性缺失 ✗ 无重试/等待/联系支持区分

④ 技术错误码暴露 ✗ "ERR_STREAM_502" 直接展示

结论

诊断报告 · 置信度 95%

四级错误 YAML 契约 + 修复后界面

pattern_id: "ERR-001"
confidence: 0.95
levels:
  fatal:     { visual_mapping: "red solid banner",    user_action: "联系支持" }
  transient: { visual_mapping: "amber inline note",   user_action: "自动重试" }
  retryable: { visual_mapping: "amber + countdown",   user_action: "等待后重试" }
  degraded:  { visual_mapping: "blue subtle badge",   user_action: "继续使用" }

案例二 · PRO-001 过程状态诊断

AI 在"思考中"到底在干什么？

用户面对"思考中"的三个问题

Q1

它卡住了吗，还是还在工作？

Q2

还要等多久？我该继续等吗？

Q3

它在做哪一步？查资料还是写答案？

一个转圈 + "思考中..." 三个字，一个都答不上来

演示

对比演示：过程透明化

Perplexity 阶段提示 vs 契约四阶段卡

BEFORE · 单一模糊提示

⠋ Searching...
⠋ Reading...
⠋ Wrapping up...
// 有阶段感但无语义：用户不知道每步多久、失败在哪步

AFTER · 契约驱动的四阶段卡

✓ RETRIEVAL

检索 3 个来源 · 1.2s

✓ SYNTHESIS

整合来源信息 · 0.8s

● VERIFY

交叉验证事实 · 进行中

○ GENERATE

生成回答

拆解

四阶段认知流水线

每阶段：视觉映射 + 用户可见信息 + LLM 约束

阶段视觉映射用户可见信息LLM 约束
RETRIEVAL 检索蓝色脉冲 + 🔍来源数、来源域名必须标注引用来源
SYNTHESIS 整合蓝色流动 + ⚙整合进度不得引入来源外事实
VERIFICATION 验证紫色扫描 + ✓验证条目数矛盾信息必须标记
GENERATION 生成青色流式 + ✎逐字流式输出与验证结论保持一致
契约

PRO-001 YAML 契约与根因

透明性与可追溯是不可变边界

pattern_id: "PRO-001"
semantic_domain: "process"
phases:
  - { id: retrieval,    label: "检索来源",  motion: "pulse"   }
  - { id: synthesis,    label: "整合信息",  motion: "flow"    }
  - { id: verification, label: "交叉验证",  motion: "scan"    }
  - { id: generation,   label: "生成回答",  motion: "stream"  }
immutable_boundaries:
  transparency: "任何阶段不得静默超过 2s"
  traceability: "每阶段产物必须可被点击追溯"

表面根因

"思考中..." 文案无任何阶段语义

结构根因

前端只接收 isLoading 布尔值，四个推理阶段被坍缩成一个状态

修复方案

定义 phase 枚举语义令牌，后端逐阶段上报，前端按契约渲染四阶段卡

两个案例，同一套方法

ERR-001 和 PRO-001 的根因相同：布尔状态坍缩了语义。修复路径也相同：快照取证 → 三层判定 → 模式卡片归档 → YAML 契约 → 编译到四端。
