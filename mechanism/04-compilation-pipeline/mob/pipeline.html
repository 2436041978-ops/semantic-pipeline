# === 组织级不可突破红线（基线层）===
在生成任何错误状态界面时，必须遵守：
【安全类约束 — 强制执行】
- 禁止所有错误状态共用同一种红色视觉表达
- 必须区分 Fatal / Transient / Retryable / Degraded 四级
- Fatal 必须提供恢复路径（刷新/导出历史）
【清晰类约束 — 警告模式】
- 每个错误级别必须提供明确的用户行动指引
- 禁止仅显示"出错了"等模糊文案
# 消费者：Error-State-Generator · AI 生成工具
# === 前端团队扩展（v2.0.1 · 接口人：王五）===
【Degraded 状态补充约束】
- 必须在降级提示中显式列出可用功能清单
- 禁止使用"部分失败""服务异常"等模糊表述
- 必须说明"已生成的内容仍然有效"

【组织级基线层】来源：规范评审组 · v1.1.0

安全类（不可突破）：
□ 是否区分了 Fatal/Transient/Retryable/Degraded 四级？
□ 每级是否有不同的颜色（红/灰/黄/蓝）？
□ 是否禁止了所有错误共用同一种红色？
清晰类（建议遵守）：
□ 每级是否有明确的用户行动指引？
□ Fatal 是否有恢复路径？
□ Retryable 是否有倒计时或升级入口？

关键设计：同一语义的不同表达

Prompt 前缀里的 "status.critical" 和 JSON Schema 里的 "status.critical" 指向语义字典中的同一个绑定；ESLint 的"禁止同一颜色"和 Checklist 的"是否禁止共用红色"是同一约束的不同表达。四种格式共享同一信源——契约升级时全部自动重编译。
