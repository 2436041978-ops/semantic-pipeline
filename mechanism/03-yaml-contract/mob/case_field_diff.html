ERR-001 · Before / After

自然语言规范 vs YAML 契约字段

BEFORE · 自然语言规范

"错误状态要分级显示。严重的用红色，一般的用黄色，轻微的用灰色。文案要写清楚，让用户知道该做什么。高危操作要二次确认。"

❌ 机器不可执行 ❌ 无场景归属 ❌ 无行为约束 ❌ 无红线

"严重"是形容词，机器不知道什么算严重 · "写清楚"是主观标准，走查各执一词 · "高危操作"没有明确定义

AFTER · YAML 契约字段 
intent_id: "ERR-001"
version: "v1.1.0"
semantic_domain: "observational"
applicable_products: ["ChatGPT", "Kimi", "DeepSeek"]
semantic_tokens:
  error_severity:
    fatal:
      visual_mapping:
        color_token: "status.critical"
        motion_token: "pulse.red.urgent"
        icon_token: "alert.octagon"
      user_action: [刷新页面, 导出历史]
    retryable:
      visual_mapping:
        color_token: "status.warning"
        icon_token: "clock"
immutable_boundaries:
  - rule: "禁止所有错误共用同一种红色"
    violation_action: "block"
✓ 机器可执行 ✓ 场景归属 ✓ 行为约束 ✓ 红线阻断
A/B

A/B 对比实验

同一 Prompt"生成限流提示"，未注入 vs 注入契约

未注入契约

Prompt: "生成一个限流提示界面"

🚨 请求过于频繁

系统出现严重错误，请刷新页面重试。

⚠️ AI 看到"严重"就用了红色，限流被渲染成致命错误——用户看到红就刷新，其实等 30 秒自动恢复

注入契约（ERR-001.yaml 前缀）

⏱️ 请求频率已达上限

请在 42 分钟后重试，或升级至 Plus 获得更高限额。

✓ AI 按 status.warning 生成黄色时钟 + 倒计时 + 升级入口，用户知道这是限流，不是系统崩溃

7 字段差异矩阵

自然语言痛点 → YAML 解法 → 机器获得的能力

intent_id

Before："那个错误状态的东西" ❌ 无唯一标识

After：ERR-001 精确指向 ✓ 验收引用版本号，Diff 可见

description

Before："严重的用红色" ❌ "严重"是形容词

After：现象+根因+后果 ✓ 一句话说清边界

semantic_domain

Before：文档里没提 ❌ 机器不知道场景归属

After：observational ✓ 跨层禁止可执行

applicable_products

Before：无 ❌ 不知在哪个产品生效

After：["ChatGPT","Kimi","DeepSeek"] ✓ 全局/局部明确

semantic_tokens

Before："文案要写清楚" ❌ 主观标准各执一词

After：四级枚举 + 颜色+行为+文案 ✓ 每级绑定唯一视觉映射

llm_constraints

Before："高危操作要二次确认" ❌ 写在文档里 AI 不读

After：生成前注入 Prompt ✓ 直接拦截，不按概率生成

immutable_boundaries

Before：无 ❌ 没有"绝对不能碰"的红线

After：violation_action: block ✓ 违反直接阻断

→

机器可执行结构

YAML 字段可被机器在三个时间点校验

生成前 · Prompt 前缀注入

AI 按约束生成，不按概率生成

生成中 · Schema 校验

前端按字段映射渲染，不硬编码颜色

生成后 · CI 拦截

缺少恢复路径的致命错误在提交时阻断

走查是事后，机器拦截是事前。事前拦住比事后修改便宜 100 倍。
