Schema-As-Code 验证层 · 契约的机器防线

契约的机器防线 Machine Defense

契约不是文档，是机器执行的拦截规则。
写的时候防呆、入库前校验、入库后对账——三道闸贯穿契约全生命周期。

1

结构违规可被拦截

缺字段、版本号非法、层级挂错 → 被字段完整性 / 结构合法性校验阻断，错误定位到具体字段路径。

2

语义违规可被拦截

description 无现象根因后果、llm_constraints 不可判定 → 被契约评审 + 可判定性校验拦截。

3

同步违规可被拦截

手改产物、下游拿过期版本 → 被产物哈希校验 / 版本声明对账标记告警。

1
入口防呆
Gate 1 · 写的时候防呆——格式错误在产生前就消除
手写 YAML 
intent_id: "ERR-001"
description: "错误状态规范"
semantic_domain: "observational"
semantic_tokens:
  error_severity:
    fatal:
      visual_mapping:
        color_token: "status.critical"
      user_action:
        - label: "刷新"
          action: "refresh"
    transient:
      visual_mapping:
        color_token: "status.neutral"
      user_action:
        - label: "等待"
          action: "wait"
llm_constraints:
  - "文案要友好一点"
immutable_boundaries:
  - boundary_type: "safety"
    rule: "禁止全部红色"
    violation_action: "block"

手写问题：

缺 version 字段
缺 applicable_products 字段
llm_constraints 不可判定（"友好一点"）
缩进错误风险
表单生成

契约编辑器表单

intent_id ERR-001 ✓
version 1.0.0 ✓ SemVer
semantic_domain observational ✓ 字典已注册
applicable_products ["*"] ✓
llm_constraints
"禁止所有错误状态共用同一种红色视觉表达" ✓ 可判定
immutable_boundaries
safety / block ✓

✓ 表单校验通过：7 字段齐全、版本 SemVer、约束可判定、字典引用合法

→ 不是"写错后拦截"，是"写不出来"——表单字段与 schema/intent-schema.json 同源生成，格式错误在产生前就消除。

2
入库校验
Gate 2 · 入库前五项前置校验——任一不过即阻断

五项安检 + 对抗用例拦截结果

安检项 查什么 对抗用例（故意写错） 拦截结果 错误定位
覆盖层存在性 semantic_domain 是否在字典预定义列表 semantic_domain: "custom_domain" ✕ BLOCKED SEMANTIC_DOMAIN_UNDEFINED
绑定存在性 color_token / motion_token / icon_token 是否在字典 color_token: "status.unknown" ✕ BLOCKED BINDING_UNDEFINED
场景一致性 scenario_mappings 是否指向字典已注册的覆盖层 scenario_mappings 引用未注册 domain ✕ BLOCKED SCENARIO_DOMAIN_MISMATCH
字段完整性 7 个顶层字段是否齐全、version 是否符合 SemVer x.y.z 缺 immutable_boundaries + version: "1.0" ✕ BLOCKED FIELD_INCOMPLETE / VERSION_INVALID
结构合法性 YAML 语法、缩进、类型是否符合 schema；必填子字段检查 缩进错误 + 缺 llm_constraints 子字段 ✕ BLOCKED SCHEMA_VIOLATION / SUBFIELD_MISSING

对抗用例
全部拦截
100%
拦截率
结构违规属确定性判定

安检项
任一不过即阻断

错误响应格式：{ code, message, location }

[BLOCKED] FIELD_INCOMPLETE
message: "契约缺少必填字段: immutable_boundaries"

3
同步防线
Gate 3 · 入库后对账——产物与源契约持续一致
版本声明对账

每个编译产物头部嵌入版本声明，消费方加载时核对。

# === COMPILED FROM ===
# source: contracts/ERR-001.yaml
# version: 1.1.0
# compiled_at: 2026-07-13T09:00:00Z
# hash: sha256:abc123...
# =====================
手改拒绝

compiled/ 目录全部由编译管线产出，CI 校验产物哈希。

[CI REJECTED] HASH_MISMATCH
compiled/prompts/ERR-001.md
expected: sha256:abc123...
actual: sha256:def456...
Action: REJECT — 手改产物禁止合入
消费追踪

追踪每个产物被哪些下游消费，版本不一致自动告警。

Prompt 前缀: v1.1.0 ✓
JSON Schema: v1.1.0 ✓
CI 规则: v1.0.0 ⚠ 过期

告警规则

提交后 5 分钟未触发 CI

契约入库后编译管线未启动 → 立即告警

编译通过后 10 分钟未注入

产物未同步到下游消费点 → 立即告警

注入后 1 小时未同步 DesignOps

Checklist / 走查清单未更新 → 告警

≠

调整前 vs 调整后

DesignOps 真实踩坑场景：三道闸就位后的走向完全不同

对比项 调整前（真实踩坑场景） 调整后（三道闸就位）
过期产物 下游用 v1.0.0，契约已到 v1.1.0，无人察觉 产物头部版本声明与契约库对账，不一致即标记告警
手改产物 直接改 compiled/ 下的 Prompt 前缀，评审才发现对不上 CI 校验产物哈希与编译记录，手改产物被拒绝合入
结构写错 缺字段、版本号乱写，入库后下游才报错 编辑器表单层防呆 + 入库五项校验阻断，错误定位到字段路径
归因留痕 "谁改的、什么时候改的"靠问 结构违规按字段路径归因，同步违规按消费方归因，全程留痕

诚实清单

设计层已完成 vs 执行层需补齐

已完成的（设计层）

三类违规的用例定义与预期结果
入库五项校验的判定逻辑与错误结构
版本声明格式与同步对账规则设计
三层编译验证的流程定义
契约加载与解析的单点演示（演示环境）

需工程团队补齐的（执行层）

契约编辑器工程实现（里程碑 M3）
schema/intent-schema.json 与编辑器表单同源生成机制
产物哈希校验 CI + 消费状态数据库
测试用例集（语义验证）与交叉比对工具（一致性验证）
/api/contracts/validate 与 /api/contracts/compile 生产部署

→ 这不是缺陷，是分工：本篇定义"守住契约应该测什么、通过标准是什么"，工程团队负责"怎么自动化跑、怎么接入生产环境"。

契约不是"写好了就完事"，是"一直在工作"
