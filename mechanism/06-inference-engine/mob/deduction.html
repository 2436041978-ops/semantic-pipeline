四层推演机制 Four-Layer Inference

把语义漂移拆成四层逐步定位：语法 → 语义 → 安全 → 美感

不是等生成完了人眼走查，是在生成过程中逐层拦截。逐层校验、逐层短路，契约有效性从"祈祷"变成"可证"。

1

生成中拦截成本最低

事后走查覆盖率仅 ~20%；生成中拦截在产出前阻断，修复成本趋近于零

2

逐层短路、逐层定位

上层阻断则下层跳过；断裂点定位到具体契约条款

3

对抗用例即回归资产

契约变更后全量重跑，拦截能力只升不降

四层推演演示：限流用了致命红

AI 生成快照 → 逐层校验、逐层短路

输入：AI 生成组件语义快照

{
  "component_type": "Alert",
  "visual": {
    "color": "red",        // ← 问题：限流用了致命红
    "background": "solid",
    "icon": "warning"
  },
  "copy": {
    "title": "Error",
    "description": "请求过于频繁，请稍后再试",
    "tone": "urgent"
  },
  "interaction": {
    "dismissible": true,
    "actions": ["retry"]   // ← 问题：应"等待"而非"重试"
  },
  "context": "system_error"
}

Layer 1 · 语法层

✓ 通过

JSON 结构完整，component_type / visual / copy / interaction / context 全部存在

Layer 2 · 语义层

✕ 断裂

文案"请求过于频繁" → 匹配 ERR-001 (retryable)
契约要求 color_token = "status.warning"（黄色）
AI 输出 red → 映射到 status.critical（致命）
修正建议：color "red" → "yellow"

Layer 3 · 安全层

✕ 阻断

违反 immutable_boundaries.safety："禁止所有错误状态共用同一种红色"
用户后果：无法区分"限流"与"系统崩溃"
产出被拦截，PR 无法合并

Layer 4 · 美感层

— 未执行

安全层已阻断，美感层被短路跳过，节省计算

↻

推演报告 → 修正 → 全过

断裂点定位到令牌级，修正指令可执行

断裂点 + 修正指令

断裂点：
· 语义层 visual.color → retryable 映射 status.critical
· 安全层 immutable_boundaries.safety → 红色共用
· 契约条款 ERR-001.yaml · error_severity.retryable

修正指令：
· visual.color: "red" → "yellow"
· visual.icon: "warning" → "clock"
· interaction.actions: ["retry"] → ["wait", "upgrade"]
· copy.title: "Error" → "Too Many Requests"

修正后重跑：四层全部通过

L1 语法层 ✓

结构完整

L2 语义层 ✓

retryable → warning

L3 安全层 ✓

无红色共用

L4 美感层 ✓

文案精度合格

✓ 产出允许发布 —— 契约有效性从"祈祷"变成"可证"

↔

与 Prompt 前缀 / CI 的关系

三层校验互补，不是替代

上游 · Prompt 前缀注入

预防

时机：生成前 · 降低违规概率 · 局限：无法判定结果是否遵守

中游 · 四层推演

拦截

时机：生成中 · 逐层校验短路 · 优势：断裂点定位到令牌级别

下游 · CI 提交检查

兜底

时机：提交后 · 静态规则校验 · 局限：修复成本高（已编码）

Prompt 前缀是"预防针"，四层推演是"安检门"，CI 是"兜底网"。四层推演是唯一能在生成过程中判定结果是否遵守契约、并定位到具体断裂点的机制。

契约有效性从"祈祷"变成"可证"

语法 → 语义 → 安全 → 美感，逐层校验、逐层短路。生成结果可被判定为符合或不符合契约，断裂点可定位到具体令牌级别。
