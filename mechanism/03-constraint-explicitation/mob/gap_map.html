诊断

模式诊断 · 为什么会断裂

根因：缺少 error_severity 语义令牌

组件类型 · Alert / Message 根因 · 缺少 error_severity

断裂机制分析

系统缺少 error_severity 语义令牌时，AI 与前端的 fallback 逻辑是："错误 = 红色"。来自两个隐含假设：
1 · Prompt 隐含假设：system prompt 写"错误提示使用红色背景"，未区分级别
2 · 组件库隐含假设：Alert 默认红色 solid，没有暴露 severity 属性
结果：无论 500（fatal）、429（retryable）还是网络超时（transient），都渲染成同一个红色 Alert。

编译

编译输出 · 一份 YAML 四种消费格式

YAML → Prompt 前缀 / Checklist / CI 规则

intent_id: "ERR-001"
semantic_domain: "observational"
semantic_tokens:
  error_severity:
    fatal:
      color_token: "status.critical"
      motion_token: "pulse.red.urgent"
      icon_token: "alert.octagon"
      user_action: [refresh, export_history]
    transient:
      color_token: "status.neutral"
      motion_token: "spinner"
      icon_token: "loader"
      user_action: [wait, retry]
    retryable:
      color_token: "status.warning"
      motion_token: "none"
      icon_token: "clock"
      user_action: [wait_countdown, upgrade]
    degraded:
      color_token: "status.info"
      motion_token: "none"
      icon_token: "info.circle"
      user_action: [continue, retry_simplified]
immutable_boundaries:
  - boundary_type: "safety"
    rule: "禁止所有错误状态共用同一种红色"
    violation_action: "block"
  - boundary_type: "clarity"
    rule: "每个错误级别必须提供明确行动指引"
    violation_action: "warn"

通过准则

• 单元测试 100%：每个 severity 级别有独立视觉映射测试
• 集成测试 100%：Prompt 生成组件与前端渲染结果一致
• 回归测试 100%：禁止任何两个不同 severity 使用相同红色
• 同义词防火墙："严重"必须被替换为 "Critical"
• 边界校验：fatal 必须提供刷新/导出路径，retryable 必须提供倒计时/升级路径
