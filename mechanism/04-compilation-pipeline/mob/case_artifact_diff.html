同一份契约的四角色消费格式

同一份契约，手工维护四份产物 vs 编译管线自动生成，分别长什么样？产物层的一致性，靠人维护为什么守不住？

1

同一条规则，两种形态

手工：四份独立文件各自解读。编译：一份 YAML → 四份产物

2

一致性靠人守不住

10 条规则 × 4 份产物 × 5 条产品线 = 200 个人脑对齐点

3

差别不可替代

版本对账检测过期、哈希校验拦截手改、消费追踪定位滞后——从"人盯"变"机管"

Δ

变更场景：限流提示增加倒计时

retryable 级别必须显示倒计时 + 升级入口。15 天后，四份产物分别是什么状态？

BEFORE · 手工维护四份产物
Prompt 前缀（AI 用） v1.0.0 · 过期

维护者忘了更新。AI 继续生成无倒计时的限流提示。

Checklist（走查用） v1.1.0 · 最新

走查按新标准判不合格，但 AI 按旧版生成。

JSON Schema（前端校验） v1.0.0 · 过期

前端手工加字段，拼写与文档不一致（count_down vs countdown），校验形同虚设。

CI 规则（流水线） 未更新

CI 工程师没收到通知，不拦截无倒计时的限流提示。

⚠️ 四份产物，四个版本。走查按新版判不合格，AI 按旧版生成，前端不拦截，CI 不阻断——没有任何机制能回答"这四份产物现在一致吗"。

AFTER · 编译管线自动生成 
# 单一来源：ERR-001.yaml
error_severity:
  retryable:
    visual_mapping: { color_token: "status.warning", icon_token: "clock" }
    user_action:
      - { label: "等待倒计时", action: "wait_countdown" }  # ← 新增
      - { label: "升级套餐",   action: "upgrade" }        # ← 新增
Prompt 前缀 v1.1.0 · 已编译
Checklist v1.1.0 · 已编译
JSON Schema（countdown 自动注入，拼写一致） v1.1.0 · 已编译
CI 规则（自动拦截缺 countdown） v1.1.0 · 已编译

✓ 一处修改，四处同步，零遗漏。每份产物携带版本身份证——过期可检测，手改可拦截，滞后能定位。

逐维度差异对照

六个维度：手工维护 vs 编译管线 · 左右滑动

维度Before（手工）After（管线）差异能力
事实源 无。四份产物各自解读，同一条规则四种理解 YAML 契约唯一来源，争议有仲裁依据 单一真相源
同步方式 四个人各自记得、各自有时间、各自理解 Git 提交 → 钩子编译 → 四份产物自动生成 一处修改四处同步
版本标识 产物无版本信息，一个月后不知新旧 头部嵌入：源契约 / 版本 / 编译时间 / Commit Hash 过期可检测
一致性证明 无法证明。走查合格但 AI 生成旧版 三层编译验证：结构 / 语义 / 交叉比对 一致性可证
手改风险 产物即源头，改了没人知道，两套"真相"并存 compiled/ 禁止手改，CI 校验哈希拒绝合入 完整性机管
字段适配 同一份内容发所有人，Prompt 里塞 Schema 语法 字段裁剪：每份只拿自己需要的 精准投递
ID

产物身份证

以前产物只有内容；现在携带来源 + 版本 + 一致性证明

Prompt 前缀（带身份证）

# === COMPILED PRODUCT ===
# source: intent/err-001.yaml
# version: v1.1.0
# compiled_at: 2026-07-12T13:40:00Z
# commit: a1b2c3d
# hash: sha256:9f8e7d...
# DO NOT EDIT MANUALLY
# ========================

在生成错误状态界面时，必须遵守以下语义分级：
- Fatal：红色脉冲 + 八边形警告
- Retryable：黄色提示 + 时钟图标 + 必须显示倒计时

版本对账演示

$ semantic-pipeline verify --product=prompt-err-001

[VERIFY] Product: prompt-err-001
  Product Version: v1.1.0 (commit: a1b2c3d)
  Consumer Loaded: v1.0.0 (commit: e5f6a7b)

[ALERT] Version mismatch detected!
  Expected: v1.1.0 | Actual: v1.0.0
  Lag: 1 version behind
  Action: Notify consumer owner to update

[RESULT] ❌ FAILED — Consumer running stale product

⏳ 消费方加载旧版本产物时，版本对账直接标记"消费版本滞后"，5 分钟内告警。

五角色反馈：同一根因，不同坑

产物无单一来源、无同步机制，各角色踩坑各不相同

🎨 设计师

"规范改了，Prompt 前缀还是旧的，AI 继续按老规矩生成。"

✓ 机制解：产物头部嵌入版本声明，过期自动告警

💻 前端 / AI 工程师

"Checklist 是新的，CI 规则是旧的，走查和拦截标准不一致。"

✓ 机制解：单一来源编译，三层验证保证一致性

📋 DesignOps

"有人嫌麻烦直接手改了编译产物，两套'真相'同时在线。"

✓ 机制解：compiled/ 禁止手改，CI 拒绝手工修改

🏗️ 语义翻译设计师 / 体验架构师

"模式库维护成本高，每次变更要改四份文件。"

✓ 机制解：改一次 YAML，四处自动同步

📊 管理层 / 决策者

"规范更新了，但不知道哪些产物还没跟上。"

✓ 机制解：消费状态数据库，变更 5 分钟告警

不是"多了一种工具"，是"一致性从人管变成机管"

手工维护只解决了"有产物"，编译管线解决了"产物一致"。10 条规则 × 4 份产物 × 5 条产品线 = 200 个需要人脑对齐的点。单一来源不是工程洁癖，是一致性在规模化下的唯一解。
