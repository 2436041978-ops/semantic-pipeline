能力一 · 违约动作 能力二 · 单一真身 能力三 · 前置拦截 能力四 · 证据门槛
实验一

规则必须带"违约动作"

从"建议"变成"阻断"——三种 violation_action 的处理结果

immutable_boundaries:
- boundary_type: "safety"
  rule: "限流提示禁止用红色"
  violation_action: "suggest" | "warn" | "block"

AI 生成的错误提示组件（retryable 误用红色）：

⚠️ 请求过于频繁，请稍后再试

SUGGEST 成本：高

仅显示建议标签，AI 输出照常通过 → 事后修复

WARN 成本：中

标记警告但允许通过，需人工复查 → 走查返工

🚫 BLOCKED 成本：零

检测到 retryable 级别使用了 status.critical（红色）→ 直接拦截，错误在生成阶段被消灭

实验二

规则只能有一个"真身"

从"五份规范"变成"一份源头"——改 YAML，四种格式自动同步

YAML 真身（唯一源头）

error_severity:
  retryable:
    visual_mapping:
      color_token: "status.warning"  # ← 修改此处
      motion_token: "none"
      icon_token: "clock"
    user_action:
      - label: "等待倒计时"
      - label: "升级套餐"

↓ 编译产物（自动同步）

Prompt 前缀

"限流提示必须使用黄色（status.warning），禁止红色…"

JSON Schema

"color_token": {"enum": ["status.warning"]}

Checklist

□ 限流提示是否为黄色？

CI 规则

forbidden: {color: "#cf1322"}

✓ 单一来源验证通过

YAML 真身修改后，4 个编译产物版本号自动同步为 v1.1.0，零遗漏

实验三

规则要放在生成之前

从"事后检查"变成"前置拦截"——防线越靠前，成本越低

生成前 Prompt 注入 成本零
编码时 Schema 校验 成本低
提交时 CI 拦截 成本中
走查时 人工复查 成本高
上线后 用户投诉 成本最高

防线位置：生成前 · Prompt 注入

规则作为 Prompt 前缀，在 AI 生成界面之前进入上下文。约束从"事后检查清单"变成"前置生成条件"。

🛡️ 100% 拦截 · 错误根本不出现 零成本 · 零返工
实验四

只显化有证据的

从"拍脑袋"变成"有凭据"——证据门槛决定能否入典

入典判定：证据来源类型

✓产品界面截图（通用 AI 产品）
✓用户反馈 / 投诉记录
✓系统日志 / 数据
✗无证据，个人偏好 → 拒绝入典

证据：Perplexity

证据：Claude

ACT-001

证据：通用 AI 后台界面
