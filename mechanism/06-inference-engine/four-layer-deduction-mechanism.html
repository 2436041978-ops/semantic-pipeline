四层推演机制 Four-Layer Inference

把语义漂移拆成四层逐步定位：语法 → 语义 → 安全 → 美感。逐层校验、逐层短路。
不是等生成完了人眼走查，是在生成过程中逐层拦截。契约有效性从"祈祷"变成"可证"。

1

生成中拦截成本最低

事后走查覆盖率 ~20%，Prompt 祈祷无结果判定。生成中拦截在产出前阻断，修复成本趋近于零

2

逐层短路、逐层定位

语法断裂直接短路，不进入语义层；安全阻断直接阻断，不进入美感层。断裂点定位到具体契约条款

3

对抗用例即回归资产

契约变更后对抗用例全量重跑，拦截能力只升不降。用例不是一次性测试，是持续回归资产

?

语义校验发生在什么时候成本最低？

事后走查、Prompt 祈祷、还是生成中拦截？

事后走查

人眼检查生成结果

覆盖率：~20%
修复成本：高（已上线）
定位精度：低（"感觉不对"）
❌ 语义错误漏到线上
Prompt 祈祷

Prompt 前缀注入约束

覆盖率：无法判定
修复成本：中（生成后重试）
定位精度：无（违反无人知）
⚠ 无结果判定机制
✓ 生成中拦截

四层推演逐层校验

覆盖率：100%（逐层短路）
修复成本：趋近于零（产出前）
定位精度：令牌级别 / boundary 条款
✓ 契约有效性可证
4

四层推演演示

输入：AI 生成的限流提示组件语义快照 → 逐层校验、逐层短路

输入：AI 生成组件语义快照

{
  "component_type": "Alert",
  "visual": {
    "color": "red",           # ← 问题：限流用了致命红
    "background": "solid",
    "icon": "warning"
  },
  "copy": {
    "title": "Error",
    "description": "请求过于频繁，请稍后再试",
    "tone": "urgent"
  },
  "interaction": {
    "dismissible": true,
    "actions": ["retry"]       # ← 问题：限流应提供"等待"而非"重试"
  },
  "context": "system_error"
}
Layer 1 · 语法层 ✓ 通过

检查 JSON 结构完整性、必填字段是否存在

✓ component_type / visual / copy / interaction / context 全部存在

Layer 2 · 语义层 ✕ 断裂

检查语义映射是否匹配契约

断裂点定位

• 输入文案："请求过于频繁，请稍后再试" → 匹配模式：ERR-001 (retryable)
• 契约要求：color_token = "status.warning"（黄色）
• AI 输出：color = "red" → 映射到 status.critical（致命）
• 语义断裂：retryable 不得映射 status.critical

修正建议：将 color 改为 "yellow"，匹配 status.warning

Layer 3 · 安全层 ✕ 阻断

检查是否违反 immutable_boundaries

阻断点定位

• 违反边界：immutable_boundaries.safety
• 规则："禁止所有错误状态共用同一种红色视觉表达"
• 当前：retryable 使用了红色（与 fatal 相同）
• 用户后果：无法区分"限流"与"系统崩溃"的严重程度

阻断动作：产出被拦截，PR 无法合并

Layer 4 · 美感层 — 未执行

因 Layer 3 安全层已阻断，美感层被短路跳过

逐层短路机制：安全层阻断 → 不进入美感层，节省计算

✕

四层推演报告：产出被拦截

断裂点

• 语义层：visual.color → retryable 映射到 status.critical
• 安全层：immutable_boundaries.safety → 红色共用
• 契约条款：ERR-001.yaml · error_severity.retryable

修正指令

• visual.color: "red" → "yellow"
• visual.icon: "warning" → "clock"
• interaction.actions: ["retry"] → ["wait", "upgrade"]
• copy.title: "Error" → "Too Many Requests"
✓

修正后：四层推演全部通过

按修正指令修改后，重新运行四层推演

修正后组件语义快照

  "visual": {
    "color": "yellow",          # ← 修正：匹配 status.warning
    "background": "solid",

  },
  "copy": {
    "title": "Too Many Requests",  # ← 修正：明确语义

生成中拦截与 Prompt 前缀 / CI 的关系

三层校验形成互补，不是替代关系

上游

Prompt 前缀注入

在生成前注入约束，降低违规概率

时机：生成前
作用：预防
局限：无法判定结果是否遵守
中游

四层推演（生成中拦截）

在生成过程中逐层校验、逐层短路

时机：生成中
作用：拦截
优势：断裂点定位到令牌级别
下游

CI 提交时检查

在代码提交时运行静态规则校验

时机：提交后
作用：兜底
局限：修复成本高（已编码）

关系说明：Prompt 前缀是"预防针"，降低违规概率；四层推演是"安检门"，产出前拦截；CI 是"兜底网"，提交后最后把关。三层互补，不是替代。

四层推演的独特价值：它是唯一能在生成过程中判定结果是否遵守契约、并定位到具体断裂点的机制。
