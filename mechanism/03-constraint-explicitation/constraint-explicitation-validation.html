约束显化

把隐含的语义假设变成显式规则

设计师脑子里的"这个要危险一点"——评审会上说了三年，AI 一个字都没读到。
约束显化把它从空气里搬出来，写成机器可读的 YAML 契约，再编译为 Prompt 前缀、JSON Schema、Checklist、CI 规则。
说一次，永久生效。

问题：一个循环往复的困境

"同一个'危险'，我在评审会上说了三年。每换一个工程师、每开一条新产品线，就要重新说一遍。"

设计师在评审会上说："这个删除按钮太危险了，不能做得和普通按钮一样。"工程师点头，改了。三个月后，另一个团队用同样的 AI 工具生成后台管理界面，删除用户按钮又是蓝色实心。

问题不是"工程师没记住"，也不是"设计师没说清"——而是"危险"这个判断从未离开过设计师的脑子。它存在于评审会的空气里、存在于 Figma 注释里、存在于某篇 Wiki 的角落里，但从来没有存在于机器能读到的地方。

为什么隐性知识守不住：AI 没有上下文补偿能力

传统时代 · 隐性知识勉强够用

人画界面时，设计师和工程师坐在一起，口头传递语义判断："这个要做得危险一点。"工程师凭经验理解"危险"意味着红色、加确认框。

本质：人在替格式缺口打补丁。补丁打得了一时，打不了规模。

AI 生成时代 · 隐性知识彻底断链

AI 没有上下文补偿能力。它只消费显式输入：Prompt 里的文字、组件库的参数。当设计师说"这个按钮要危险一点"时，AI 听不到——因为这句话不在任何它消费的输入里。

AI 按概率生成最"常见"的按钮：蓝色实心主按钮。

关键判断

语义漂移不是 AI"做错了"，而是约束从未被显式传递，AI 根本没有收到信号。把漂移归因为"AI 理解力不够"，会让人去等更强的模型；把漂移归因为"约束不在输入里"，才会让人去修约束的形态。前者是等待，后者是工程。

四项能力

约束显化不是"把规范写成代码格式"，而是通过转换获得四项传统形态在原理上就不可能提供的能力。

1

规则必须带"违约动作"——从"建议"变成"阻断"

不是"建议不要用"，而是"如果用了，就阻断"

规范文档里写了"限流提示不要用红色"，但这是一句"建议"。工程师忙起来可以忽略，AI 读不到更是直接无视。

规则文件里每一条"不能做什么"，都必须附带"违反了怎么办"。 

immutable_boundaries:
  - boundary_type: "safety"
    rule: "禁止所有错误状态共用同一种红色视觉表达"
    violation_action: "block"      # ← 不是 suggest，是 block
  - boundary_type: "clarity"
    rule: "每个错误级别必须提供明确的用户行动指引"
    violation_action: "warn"       # ← 不是 note，是 warn

走查阶段

人眼看到红色，圈出来让前端改 → 改完再测，来回三轮

阻断阶段

AI 生成时用了红色 → 机器直接拦截，错误不出现

2

规则只能有一个"真身"——从"五份规范"变成"一份源头"

YAML 是真身，Prompt / Checklist / CI 规则全是自动编译产物

同一条规则写了五份——语雀一份、组件注释一份、AI 指令模板一份、测试用例一份、流水线配置一份。三个月后，语雀改了，注释没改，AI 模板还是旧版。

只保留一份"真身"，其他四种格式全部由这份真身自动编译产出。禁止手写副本。

ERR-001.yaml（真身）
Prompt 前缀
给 AI
自动编译

自动编译

改前

改一处规则，要手动追四处 → 漏一处就是版本分裂

改后

改 YAML 真身一处，四处编译产物自动同步 → 零遗漏

3

规则要放在生成之前——从"事后检查"变成"前置拦截"

防线从"检查成品"前移到"约束生成"，错误在出生前就被拦住

同一条"限流提示用黄色"的规则，放在不同环节，成本天差地别：

上线后发现

用户已投诉

成本：最高

走查时发现

代码已写完

成本：高

提交时拦截

代码未合并

成本：中

生成前注入

错误不出现

成本：零

# 同一条规则，在四个时刻接力

# 1. 生成前：Prompt 前缀前置注入
llm_constraints:
  - "限流提示必须使用 status.warning（黄色）"
  - "禁止在 retryable 级别使用 status.critical（红色）"

# 2. 编码时：JSON Schema 校验
properties:
  color_token:
    enum: ["status.neutral", "status.warning", "status.info"]
    not: { const: "status.critical" }

# 3. 提交时：CI 规则拦截
rules:
  error-severity-color:
    forbidden: { color: "#cf1322" for: "retryable" }
    action: "block"

# 4. 走查时：Checklist 人工复查
- [ ] 限流提示是否为黄色？
- [ ] 是否未使用红色？
4

只显化有证据的——从"拍脑袋"变成"有凭据"

规则入典必须有门槛：不是"我觉得"，而是"我测到了"

规则库如果变成"我觉得应该这样"的个人偏好集，信用会快速崩塌。v1.0.0 只收录 6 个有充分证据的模式，全部来自对通用型 AI 产品的界面观察：

角色视角

约束显化后，各角色的处境发生了什么变化？

"同一个'危险'，我在评审会上说了三年。每换一个工程师、每开一条新产品线，就要重新说一遍。"

解法路径

action.destructive 注册入典，绑定红色空心 + 二次确认 + 不可恢复文案。判断显化一次，全组织永久引用——设计师不再重复说"危险"，改说"查字典"。

验证方式

新团队、新产品线生成删除按钮时，约束自动在场，无需任何人口头传递。

"规范文档四百页，我不可能每次写代码前重读一遍。AI 更不可能。"

解法路径

契约编译为 Prompt 前缀前置注入 AI 上下文，约束从"需要被想起"变成"已经在场"。工程师被迫在每次生成任务里手工复述规范要点——重复、易漏、不可追溯。

验证方式

AI 输出对约束的命中率不再依赖任何人的记忆。规范不用背了——约束编译成 Prompt 前缀、Schema 和 CI 规则，在你工作之前已经在场。

"规范改了一处，三个月后抽查发现一半团队还在用旧版——没人是故意的，只是没人知道变了。"

解法路径

字典变更走 PR，触发全量重编译，四种消费格式同步换版，引用方收到影响面报告。

验证方式

DesignOps 第一次能回答"这次变更影响了哪些契约、哪些团队"——精确到清单，而非"应该都通知到了"。

"我的经验在公司十年，评审时能一眼看出问题——但我讲不清我是怎么看出来的，更别说让机器看出来。"

解法路径

专家的判定逻辑被结构化为关键词表、类型规则、校验项——直觉翻译成规则后，可被复核、可被传授、可被机器执行。

验证方式

专家休假时，诊断照常运转；专家的"一眼看出"变成组织的"逐层可验"。

"团队最大的隐性成本是'重复传递同一句判断'。"

解法路径

约束显化把它变成一次性投资：判断显化入典后，传播零成本、执行有机器保障、变更有账可查。

验证方式

约束从"口头资产"变成"组织资产"——有版本、有引用方、有折旧、有审计轨迹。

调整前后对照

工具 / 环节 调整前 调整后
评审会 约束活在空气里，人散会散 评审产出物是契约变更 PR，判断当场显化入典
规范文档 四百页散文，阅读率随厚度反比降 字典即规范：机器可消费，人可查表，篇幅不再影响执行率
AI 生成流程 约束不在输入里，AI 按概率猜 Prompt 前缀前置注入，约束在生成前已在场
变更管理 公告传播，同步靠记忆 Git Diff + 全量重编译 + 影响面报告，变更精确到引用方
