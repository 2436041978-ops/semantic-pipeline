Schema-As-Code 编译与交付层 · ④ 产物层差异

产物层差异 Product Layer Diff

同一份契约，手工维护四份产物 vs 编译管线自动生成，分别长什么样？
产物层的一致性，靠人维护为什么守不住？这个差别带来的能力是不是不可替代？

1

同一条规则，两种形态

手工维护：四份独立文件，各自解读规范。编译管线：一份 YAML → 编译为四份产物。

2

一致性靠人维护守不住

规范变了，四个人各自记得、各自有时间、各自理解。10 条规则 × 4 份产物 × 5 条产品线 = 200 个需要人脑对齐的点。

3

差别带来的能力不可替代

版本对账检测过期、哈希校验拦截手改、消费追踪定位滞后——从"人盯"变成"机管"。

Δ

变更场景：限流提示增加倒计时

规范变更：retryable 级别必须显示倒计时 + 升级入口。15 天后，四份产物分别是什么状态？

Before 手工维护四份产物
Prompt 前缀（AI 用） v1.0.0 · 过期

维护者忘了更新。AI 继续生成无倒计时的限流提示。

Checklist（走查用） v1.1.0 · 最新

走查工程师更新了。走查按新标准判不合格，但 AI 按旧版生成。

JSON Schema（前端校验用） v1.0.0 · 过期

前端手工加了 countdown 字段，拼写与文档不一致（count_down vs countdown）。校验形同虚设。

CI 规则（流水线用） 未更新

CI 工程师没收到通知。不拦截无倒计时的限流提示。

⚠️ 结果：四份产物，四个版本。走查按新版判不合格，但 AI 按旧版生成，前端校验不拦截，CI 不阻断。

没有任何机制能回答"这四份产物现在一致吗"。

After 编译管线自动生成

单一来源：ERR-001.yaml

error_severity:
  retryable:
    visual_mapping:
      color_token: "status.warning"
      motion_token: "none"
      icon_token: "clock"
    user_action:
      - label: "等待倒计时"
        action: "wait_countdown"      # ← 新增
      - label: "升级套餐"
        action: "upgrade"             # ← 新增
Prompt 前缀 v1.1.0 · 已编译

Git 提交触发编译管线 → 自动生成 → 头部嵌入版本声明。

Checklist v1.1.0 · 已编译

同一契约编译，字段裁剪为走查项，无底层语法。

JSON Schema v1.1.0 · 已编译

countdown 字段自动注入，拼写与契约一致。

CI 规则 v1.1.0 · 已编译

自动拦截无 countdown 字段的 retryable 级别错误。

✓ 结果：一处修改，四处同步，零遗漏。每份产物携带版本身份证。

版本对账可检测过期，哈希校验可拦截手改，消费追踪可定位滞后。

逐维度差异对照

六个维度对比：手工维护 vs 编译管线

维度 Before（手工维护） After（编译管线） 差异带来的能力
事实源 无。四份产物各自解读规范文档，同一条规则四种理解。 YAML 契约唯一来源。语义只有一处定义，争议有仲裁依据。 单一真相源
同步方式 四个人各自记得、各自有时间、各自理解。靠人脑对齐。 Git 提交 → 钩子触发编译管线 → 四份产物自动生成 → 通知下游。 一处修改，四处同步
版本标识 产物无版本信息。一个月后拿到文件，不知道新旧。 产物头部嵌入版本声明：源契约 / 版本 / 编译时间 / Git Commit Hash。 过期可检测
一致性证明 无法证明。走查按 Checklist 判合格，但 AI 按 Prompt 生成旧版。 三层编译验证：结构校验 / 语义校验 / 交叉比对。一致性可证。 一致性可证

产物身份证：给每份产物挂一张身份证

以前产物只有内容；现在产物携带来源 + 版本 + 一致性证明

Prompt 前缀（带身份证）

# === COMPILED PRODUCT ===
# source: intent/err-001.yaml
# version: v1.1.0
# compiled_at: 2026-07-12T13:40:00Z
# commit: a1b2c3d
# hash: sha256:9f8e7d...
# DO NOT EDIT MANUALLY
# ========================

在生成错误状态界面时，必须遵守以下语义分级：
- Fatal（系统级故障）：红色脉冲 + 八边形警告
- Transient（网络抖动）：灰色加载 + 旋转图标
- Retryable（限流）：黄色提示 + 时钟图标 + 必须显示倒计时
- Degraded（部分可用）：蓝色提示 + 信息图标

Checklist（带身份证）

# === COMPILED PRODUCT ===
# source: intent/err-001.yaml
# version: v1.1.0
# compiled_at: 2026-07-12T13:40:00Z
# commit: a1b2c3d
# hash: sha256:3a4b5c...
# DO NOT EDIT MANUALLY
# ========================

错误状态走查清单：
- [ ] 是否区分了 Fatal/Transient/Retryable/Degraded 四级？
- [ ] Retryable 是否有倒计时或升级入口？
- [ ] 是否引用了意图契约 ERR-001 v1.1.0？

五角色反馈：同一根因，不同坑

产物无单一来源、无同步机制，在五个角色身上长出的坑各不相同

🎨 设计师

"规范改了，Prompt 前缀还是旧的，AI 继续按老规矩生成。"

✓ 机制解：产物头部嵌入版本声明，过期自动告警

💻 前端 / AI 工程师

"Checklist 是新的，CI 规则是旧的，走查和拦截标准不一致。"

✓ 机制解：单一来源编译，三层验证保证一致性

📋 DesignOps

"有人嫌麻烦直接手改了编译产物，两套'真相'同时在线。"

✓ 机制解：compiled/ 禁止手改，CI 拒绝手工修改

🏗️ 语义翻译设计师 / 体验架构师

"模式库维护成本高，每次变更要改四份文件。"

✓ 机制解：改一次 YAML，四处自动同步

📊 管理层 / 决策者

"规范更新了，但不知道哪些产物还没跟上。"

✓ 机制解：消费状态数据库，变更 5 分钟告警

结论：不是"多了一种工具"，是"一致性从人管变成机管"

手工维护只解决了"有产物"，编译管线解决了"产物一致"。
没有编译管线的单一来源和同步机制，产物一致性只能靠人维护——而人维护在规模化下必然失效。
10 条规则 × 4 份产物 × 5 条产品线 = 200 个需要人脑对齐的点。
单一来源不是工程洁癖，是一致性在规模化下的唯一解。

产物层是 Schema-As-Code 的"最后一公里"

契约经编译管线翻译为四种消费格式 → 版本对账保证一致性 → 交付给四个消费方
