两次交接的压缩点定位

语义存活曲线：横向看衰减，纵向看断层位置（左右滑动）

语义维度① 意图② 设计稿③ 工程实现断层位置

读法说明

横向看：语义存活曲线，每个维度如何逐级衰减。纵向看：断层位置列把压缩精确定位到某一次交接。对于 ERR-001，所有四个维度的压缩都发生在 ①→② 或 ②→③——交付链前两环已丢失 90% 语义信息，AI 只是在最后一环继承了被压缩殆尽的输入。

STEP 3

三种交付物说三种语言

语言形态的不可互算性：机器能校验的，语义最贫瘠

设计意图 · 自然语言段落

机器不可校验

形容词与副词："应区分严重程度""需醒目警示"——不可运算

设计稿表现 · 视觉组件 + 标注

机器不可校验

样式差异与组件命名："Error Banner""Toast"——命名是字符串，无语义结构

工程实现 · 接口字段 + Props

可校验但贫瘠

枚举值与布尔值：isError: true / type: "error"——语义已被压缩殆尽

关键发现

第三栏（工程实现）是唯一机器可校验的，但也是语义最贫瘠的——机器校验介入得越晚，能守住的东西越少。只在工程实现层做校验（ESLint/Stylelint），校验的只是一个已被压缩 90% 的语义残片；真正的语义丢失发生在更早的交接环节，而那里恰恰是机器无法触及的灰色地带。

STEP 4

Before/After 修复对照

同一条限流提示，按断层地图修复前后（左右滑动）

交付环节Before（无断层意识）After（按断层地图修复）
① 意图"限流属可恢复错误"（文档第 47 页，无人引用）error_severity.retryable 注册入典，字典可查
② 设计稿设计师选 Error Banner（红），组件库没有"可恢复"分类组件库挂载令牌映射：retryable → 黄色时钟样式
③ 工程实现isError: true → type="error" → 红色error_severity: retryable → 按契约渲染黄色 + 倒计时
AI 生成读到布尔值 + 红色样式，输出全红错误条注入契约约束，输出黄色弱化提示
用户体验以为系统崩溃，刷新丢失内容看到"42 分钟后自动恢复"，等待即可

修复核心动作

不是让设计师"更仔细"、前端"更规范"，而是在每一次交接处插入语义契约：①→② 意图翻译为字典令牌（error_severity.retryable）；②→③ 组件样式与令牌建立映射（retryable → 黄色时钟）；③→AI 接口字段承载令牌而非布尔值（error_severity 替代 isError）。断层地图的价值不是"发现问题"，而是告诉 Contract 阶段契约该打进哪个桩。
